1 证据与依赖

方法试验在 tests/engineering/experiments/deepseekjson，以独有 Compose 项目名、只读根文件系统、无端口运行，只发合成新闻。证据目录：runtime/deepseek-json-lab-20261030T062135-50628（20 次、max_tokens=2048：17 次有效、3 次截断、2 次空 content、1 次非法 JSON）、runtime/deepseek-json-lab-20261030T062530-51491（20 次、max_tokens=8192：20 次有效，延迟中位 111 ms、P95 368 ms，completion 592–2124）、runtime/deepseek-json-lab-20261030T063624-53683（5 场景×4 次、思考开启、32K：20 次有效，论述均 754 字节，completion 均 459）、runtime/deepseek-json-lab-20261030T063756-54012（同场景关闭思考：19 次有效，1 次引用不存在的新闻 ID，论述均 757 字节，completion 均 212）。

结论：直连 OpenAI 兼容端点可行；输出上限不能按 2048 设，取 32768；思考模式保持开启（关闭未降低论述长度但出现一次硬错误，且省下的成本不足以抵消一次研判失败）。样本只覆盖合成场景，不能证明判断质量。

供应商文档：JSON Output 要求 response_format: {"type":"json_object"}、提示词含 json 字样与样例、合理设置 max_tokens，并明确说明有概率返回空 content；思考模式用 {"thinking":{"type":"enabled/disabled"}} 与 reasoning_effort，默认为开启且 effort=high，文档映射表中 medium 实际映射 high，可用档为 low/high/max；模型页记录 deepseek-flash 上下文 1M、最大输出 384K。地址见第 9 节。

不新增第三方 Go 依赖，只用标准库 net/http、encoding/json、crypto/sha256。

3 配置与派生文件

主配置 config/config.toml 的唯一真值：

[model_access]
enabled = false
endpoint = "https://api.deepseek.com/chat/completions"
api_key = ""
model = "deepseek-flash"
thinking = true
reasoning_effort = "high"
max_tokens = 32768
timeout_seconds = 120
max_input_bytes = 65536
max_output_bytes = 65536
budget_window_seconds = 86400
max_requests = 500
state_path = ""

校验：endpoint 必须为 https 且无 userinfo/query；model 非空；thinking 为布尔；reasoning_effort 仅 low/high/max；max_tokens 1–384000；超时与字节上限为正；max_requests=0 或正数，正数要求正窗口；启用时 api_key 非空。state_path 为空时使用 <root>/runtime/model-state.json；部署派生文件写绝对容器路径。

部署派生：tools/deploy prepare 从主配置抽取 [model_access] 写入 <profile>/judgment-worker/model.toml（0600），并把 profile 的 model_config 指向 /private/model.toml。容器只挂该文件，不再挂 config/ 整目录；主配置的其他部分（数据库口令、其他令牌）不进入 judgment-worker。

[[models]] 保留 name、model、timeout_seconds；删除 bun_path、provider、account_id。每个模型条目与全局配置合并后构造客户端；按顺序尝试，第一个成功即停，失败不切换端点。

4 请求与解析

POST {endpoint}
Authorization: Bearer {api_key}
Content-Type: application/json

{"model":"deepseek-flash",
 "messages":[{"role":"system","content":"<私有提示词>"},
             {"role":"user","content":"<渲染后的新闻>"}],
 "response_format":{"type":"json_object"},
 "max_tokens":32768,
 "thinking":{"type":"enabled"},
 "reasoning_effort":"high",
 "stream":false}

关闭思考时传 {"thinking":{"type":"disabled"}} 且不传 reasoning_effort；思考模式忽略 temperature/precision 参数，不额外发送。响应只读取 choices[0].finish_reason、choices[0].message.content、usage；reasoning_content 只计字节，不返回给上层。

解析顺序：HTTP 200 → 信封含 choices → finish_reason=="stop" → content 非空 → 字节不超 max_output_bytes。业务 JSON 由 P3 的 ParseJudgment 处理，本模块不做业务字段解释。

5 预算与状态

状态文件 JSON：{"window_start":"RFC3339","count":N,"attempts":N,"ids":["..."]}。调用前：读取状态；若 now < window_start 拒绝（时钟回退）；若窗口已过则重置；有限额且 count >= max_requests 返回 SEMANTIC_BUDGET_EXCEEDED 且不发请求；ID 在最近 256 条内返回 SEMANTIC_DUPLICATE_ID。通过后 count++、attempts++、追加 ID 并按上限裁剪，原子写后才发请求；供应商失败不退占用。

写入使用同目录临时文件、fsync、rename、目录 fsync，权限 0600，拒绝符号链接与超过 64 KiB 的既有文件；失败时本次调用拒绝，不继续沿用不确定状态。

所有错误只返回稳定码与有限上下文，不包含 Key、提示词、供应商正文、URL 或 stack；日志只记录错误码、时长和 token 计数。

7 部署

镜像从 3 个降为 2 个：factorforge-postgres 与 factorforge-core。删除 Dockerfile 的 model-build、bun 与 model 阶段，删除模型层约 347 MB（Bun 92 MB + node_modules 255 MB）。judgment-worker 使用 core 镜像，内存上限从 768m 降至 256m。

Compose：删除 FF_CONFIG_DIR → /private/config 挂载，改为 ${FF_PROFILE_ROOT}/judgment-worker/model.toml → /private/model.toml 只读；保留 model-runtime 作为状态目录。tools/deploy build 只构建 postgres 与 core；doctor 检查派生文件、端点、Key、模型、参数和状态目录可写，删除 OMP 账户绑定与目录检查。prepare 重新生成派生文件，不覆盖主配置。

8 测试与未验证边界

Go 测试使用 httptest 假供应商，覆盖：请求形状（json_object、thinking、effort、无 tools）、401/403/429/5xx、超时、断裂响应、空 content、length、非法信封、字节上限、预算窗口、跨重启去重、时钟回退、状态文件权限与原子性、错误不含秘密。Compose 验收覆盖：judgment-worker 只挂派生文件、缺 Key 失败关闭、假端点失败关闭。

未验证边界：真实私有提示词尚未定稿，试验用的是合成提示词；思考关闭的质量对照只做了 20 次/组；每日成本按实测单次约 0.005 元估算，未经历真实连续运行；供应商侧额度、并发限制和模型下线仍需运行期观察。真实调用必须显式授权，不纳入自动测试。
