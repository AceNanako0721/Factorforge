容器删除重建后保留运行日志

12 项实际 Docker 检查通过。合成子进程的 stdout/stderr 经实验包装器双写后，删除旧容器不会删除独立目录中的历史记录，新容器继续追加；大小轮转、正常终止和错误退出行为得到验证。未接入 Factorforge 生产进程，不能表述为整套 Compose 已完成。

方法结果限制复现

方法与隔离范围

从测试目录的 Go 源码交叉编译 Linux/ARM64 静态二进制，构建 FROM scratch 实验镜像。单服务 Compose 使用无网络、无端口、只读根文件系统、非 root UID/GID、cap_drop ALL、no-new-privileges、64 MiB 内存、0.25 CPU、32 个进程上限，仅挂载本次 runtime 下的合成日志目录。没有使用或修改现有项目的镜像、数据库、配置或凭据。

实验写入先追加并同步持久文件，再输出到 Docker；子进程使用独立进程组，包装器转发 SIGTERM/SIGINT，并等待输出管道排空与退出。持久文件采用 0600、非阻塞独占锁及大小轮转。此原型只用于考察方法，不冻结生产日志格式、错误处理和保留策略。

试验参数：每份持久日志最多 16 KiB，3 份备份加当前文件，总上限 64 KiB；Docker local 驱动单独设置每份 16 KiB、2 份。轮转场景生成 300 条约 1 KiB 的合成行。参数为实验值，不是生产默认或标定常数。

实际结果

检查实际结果
1. 双路输出stdout 的 BOOT 与 stderr 的 STDERR 标记同时出现在 Docker logs 和持久文件。
2. 同容器重启容器 ID 不变，Docker logs 和持久文件保留重启前输出，并出现第二次启动记录。
3. 信号传递SIGTERM 到达子进程，TERM 尾日志写入持久文件。
4. 删除旧容器对已删除 ID 执行 docker logs 失败，独立目录中的 BOOT 仍可读取。
5. 创建替代容器新容器 ID 与旧 ID 不同，新 BOOT 追加成功，旧 stdout、stderr、TERM 均保留。
6. 第二写入者同目录的第二个包装器被文件锁拒绝，原进程继续运行。
7. 正常停止子进程最后的 TERM 被保留，容器以 0 退出。
8. 轮转容量与权限恰好 4 个日志文件，均不超过 16 KiB，模式均为 0600，总占用 64795 字节，低于 65536 字节上限。
9. 轮转内容最新 FLOOD_END 与 TERM 保留；最早 BOOT 已按保留上限淘汰，明确证明“持久化”不等于无限保留。
10. 异常退出码子进程主动退出 37，容器保持退出码 37，退出前日志已排空保存。
11. 不可写目录只读挂载导致包装器以 73 拒绝启动，输出稳定错误码，子进程没有启动。
12. 既有服务试验前后原有 34 个运行容器的 ID 和启动时间一致。

所有本次实验容器和镜像已回收；合成日志、Compose 场景配置、构建日志及 result.json 保留在被忽略的 runtime/docker-log-lab-20261030t044256-16639。未连接模型、交易所、生产数据库或真实业务服务。check-layout 与本实验目录的 go vet 均通过。

结论与未验证边界

可采用“Docker 近期排障日志 + 独立持久化运行日志 + PostgreSQL 业务审计”的分工；只配置 Docker 日志轮转不足以满足跨容器删除保留要求。仅挂载一个目录也不会自动捕获 stdout/stderr，必须实际接入写入或采集机制。

  1. 这是合成进程的 Linux/ARM64 实验，不是生产 Go/Bun/PostgreSQL 的日志接入验收，也没有启用完整 Factorforge Compose。
  2. 未测试宿主断电、SIGKILL、真实磁盘满或 I/O 失败、子孙进程逃离进程组、长时间高负载；文件同步不证明这些场景零丢失。
  3. 轮转按字节拆分，记录可能跨文件边界；生产格式、服务/运行关联字段、脱敏、按时长保留和总容量需要在设计中明确。
  4. 实验在日志不可写时拒绝启动；生产运行中磁盘故障如何告警、降级并保证减险/保护继续，需要结合交易门禁设计，不能直接照搬“杀死执行进程”。
  5. 持久目录不等于备份；数据库中的订单、成交和风控审计继续作为业务事实，不能由控制台日志替代。数据卷备份恢复与跨主机迁移另行验收。

本次未改变已发布业务式样、设计或 E15/E20 的运行准入状态，VERSION 保持 2.19.6。正式生产接入须先修订对应设计及当前规划状态，再实现，实验代码不得直接挂入生产入口。
