# 交易层应急与恢复预案

本预案说明交易层（P1）或主执行进程失效时，怎样安全处置持仓并恢复自动运行。它不改变交易政策；对应的设计见 [交易系统层设计书](../01_交易系统层设计书.md)。

## 事先登记

在私有配置或运维档案中登记：

- 账户与渠道，以及经核验的普通单和条件单入口；
- 事先批准的触限政策（减险方式、恢复条件）；
- 操作者与独立复核者；
- 隔离旧执行进程及其凭据出口的方法；
- 事实证据的保存位置，以及时钟、存储和恢复的时间预算。

没有独立复核者或有效的官方入口时，不能启用实盘。

**启动新的主执行进程之前**，必须确认旧进程已停止，且它的出口和凭据不能再签名。数据库租约过期只表示失去本地执行权，不能代替出口隔离。`executor-fence` 记录隔离事实和当前代次；不要仅凭时间到期就登记隔离成功。

## 处置步骤

1. 在官方渠道核对账户、产品和持仓方向，记录核对时间和原始业务编号。
2. 停止自动增险，隔离旧执行进程及其凭据出口。系统可用时先用 `stop` 持久停止。
3. 在官方渠道分别查询普通单、条件单、实际仓位和资金。系统不可用时以官方渠道的事实为准，不依赖本地缓存。
4. 撤销增险单，核对累计成交和终态；保留必要的减仓型保护。撤单响应丢失按“结果未知”处理，不重复建立新风险。
5. 按事先批准的政策减险，并核对残仓。保护触发不等于已经退出；不得因本次盈亏临时放宽止损。
6. 记录每一笔人工成交、自动减仓、强平和结算的外部编号、前后数量、真实入场价、现金差额、币种、规则版本和证据引用。不知道的现金差额不能填 0。
7. 数据库和接口恢复后，用 `external-import` 导入确切的事实。成交回执用 `external_fill_ids` 关联到已包含其资金和仓位变动的外部事实，避免对账时重复入账。导入会提升归属代次、阻止旧目标补仓，并进入 `RECOVERY_CHECK`；相同外部编号去重，不覆盖历史。
8. 用 `execution-live --recover-only` 查询渠道的订单、成交、收入、仓位、保护和账户。查询不到或差额未消除时，保持恢复核验。
9. 完成保护与归属核验后，由有 `external:resolve` 权限的操作者签署解释。跨币种或跨账户的现金差额要有明确的事实来源，不能靠覆盖账户投影来修正。
10. SIM 运行 `reconcile`；LIVE 运行 `execution-live --recover-only` 取得当前版本的渠道报告，再由有 `run:resume` 权限的另一名操作者恢复。报告之后账务、规则或归属又有变化时要重新核验。仍有风险锁、结果未知、未确认的保护或外部差额时，恢复会被拒绝。

旧目标不会自动重新增险；上层要以新的目标版本和归属代次重新提交。

## 演练

每次演练记录：环境与账户、开始和结束时间（UTC）、触发的故障、操作者与复核者、旧进程与出口隔离的证据、普通单和条件单及资金的前后快照、外部编号、事实导入回执、保护确认、对账报告、恢复回执、失败与未决事项。真实记录只保存在私有运维档案中，不进入仓库。

仓库的测试用本地 PostgreSQL 和独立的接口、命令行与执行进程，演练“停机 → 人工平仓事实 → 导入 → 拒绝提前恢复 → 归属核验 → 对账 → 独立恢复”，所用渠道事实和凭据都是虚构的。这些测试不能代替在官方渠道上的现场演练。

不要在系统失效时临时编写未经验证的离线签名下单脚本。
